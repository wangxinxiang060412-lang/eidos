# UI/UX Audit Framework, Scoring & Severity Rubric

本审查体系用于存量项目体验诊断与新项目交付前门禁评估。**铁律：严禁在没有运行观察、代码依据或截图证据的情况下给项目打虚高分。**

---

## 1. 九维度加权评分模型

默认权重如下（可根据项目类型微调并说明原因，例如游戏 UI 调高视觉/HUD 与性能权重、工具类调高功能与易用性权重，权重总和必须为 100%）：

| 审查维度 | 默认权重 | 10 分标杆标准（优秀发布级） |
|---|---:|---|
| **1. 功能完整性与交互闭环** | **20%** | 所有控件真实可用、20 种适用状态闭环完整、数据持久化与错误恢复无漏洞 |
| **2. 用户习惯与易用性** | **15%** | 完全贴合用户心智与肌肉记忆、零额外学习成本、低认知负荷、误操作可撤销 |
| **3. 视觉设计与美术质量** | **15%** | 气质契合产品、层级清晰、无 AI 模板病、对比度/对齐/色彩/图标工艺精湛 |
| **4. 信息架构与导航** | **10%** | 层级合理、高频 1–3 步可达、返回保留状态、深层链接与系统返回无死胡同 |
| **5. 动效与交互连续性** | **10%** | 有因果起止、不拖慢操作、可打断、落位零跳变、尊重减少动态效果 |
| **6. 设计系统与一致性** | **10%** | 统一语义 Token、亮暗主题一致、同功能组件跨页表现统一、不过度抽象 |
| **7. 性能与运行稳定性** | **10%** | 启动快、响应达标（INP ≤200ms / 稳 60fps）、大列表流畅、无内存泄漏与报错 |
| **8. 屏幕及设备适配** | **5%** | 多尺寸重排得当、安全区/键盘避让正确、横竖屏与长文本不溢出 |
| **9. 无障碍体验** | **5%** | 达 WCAG 2.2 AA、键盘焦点清晰不被遮挡、读屏语义准确、不单靠颜色编码 |

### 计分纪律
- 每个维度按 **0–10 分**客观打分，加权求和得总分（满分 100）：
  - **90–100**：标杆发布级，仅余 P3 锦上添花细节。
  - **80–89**：良好可发布，无 P0，P1 已清零或有明确排期，存在少量 P2 体验瑕疵。
  - **70–79**：基本可用但体验粗糙，存在明显层级、一致性或局部流程摩擦。
  - **60–69**：勉强能跑，存在显著交互缺陷、AI 模板味或状态缺失，不建议直接发布。
  - **< 60**：不合格，存在核心流程中断或严重可用性阻塞。
- **未核查维度不得打 9–10 分**：若某维度因环境限制未能实测（如无法在真机测性能或录屏看动效），必须在评分表旁标明 `Unverified / 估算上限` 并说明依据。

## 2. 问题严重度分级（P0 – P3）

| 级别 | 名称 | 严格判定标准 | 处理要求 |
|---|---|---|---|
| **P0** | **致命阻塞 / 一票否决** | 核心功能无法使用、假按钮/断流、提交丢数据/误删无保护、严重崩溃、主流程关键文本完全看不清或无法点击、严重违反平台安全区导致操作被挡死 | **发布一票否决！**即使视觉得满分也绝不能通过验收，必须立即修复 |
| **P1** | **主路径重要缺陷** | 显著拖慢核心任务、缺少关键空态/错误重试/防重复提交、严重违背用户习惯与平台返回手势、核心对比度不达标（<4.5:1）、键盘焦点陷阱、明显掉帧/卡顿 | **上线前必须修复** |
| **P2** | **体验与一致性问题** | 视觉层级弱、存在明显 AI 模板化设计（嵌套卡片/滥用胶囊/紫蓝渐变）、间距/圆角/图标风格不统一、文案生硬、动效略显生硬或缺少微反馈 | **纳入本轮优化计划高优解决** |
| **P3** | **细节打磨（Nice to have）** | 极细微光学居中微调、锦上添花的微动效或触觉润色、非关键页面的美化提升 | 按资源排期，**绝不为了 P3 引入回归风险** |

## 3. 每条审查问题必填 9 字段

输出审查报告（使用 [audit-report.md](../templates/audit-report.md)）时，每一条问题必须完整记录：
1. **位置**：所在页面、路由及组件/文件路径
2. **当前表现**：客观描述截图/运行中观察到的现象
3. **产生原因**：设计逻辑缺失还是代码实现问题
4. **用户体验影响**：具体如何阻碍用户理解、效率或信任
5. **对应设计原则**：锚定具体原则（如 Fitts's Law / WCAG 2.2 SC 1.4.3 / Anti-AI-UI #4）
6. **修改方案**：具体可执行、最小改动范围的改造建议
7. **优先级**：`P0` / `P1` / `P2` / `P3`
8. **验收方式**：明确的复测路径、目标视口或断言标准
9. **实际验证结果**：`待修复` / `已修复并复测通过（附证据）` / `受限未验证`
